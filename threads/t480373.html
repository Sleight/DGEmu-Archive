KKirie MotobaJan 06 2014, 06:51 AM

Quick tutorial:

I haven't actually worked with SQL Server 2012 Express yet, but I constantly use SQL Server 2005 Standard and 2008 Enterprise at work, so I know how to get around it fairly well.

2012 might have adapted the GUI with a ribbon at the top, but the rest should be similar.

 

Well, you got SQL Server 2012 Express on your computer.

 

Basically, now you have an SQL Server services running on your background all the time.

The tool you'll be fully dependent on for now is SQL Management Studio 2012.

 

Run that tool.

To connect, you choose:

Server type: Database Engine

Server name: localhost or your computer name

Authentification: SQL Server Authentification

Login: sa

Password (empty by default, or specify one if you did during setup)

 

Once logged in, on the left, you have an object explorer.

By default, you should see your server name there expanded with many options.

Right-click on "Databases" and select "New Database".

 

Specify your database name and preferably, leave the owner to <default> for now.

 

Once done, expand the database section in your object explorer, you should notice your new db there.

Right-click that, choose "New Query".

You should see a new query window appear. Type in your SQL queries there and click on "Execute" to perform them. (At this point, you should be making your tables and datatypes for every field)

 

If you're lazy, expand your database in the object explorer. You should see an "Tables" subfolder.

Right click it, and select "New Table", and have fun making your tables with a GUI.

You can also create views the same way. That's basically what you want to use for your project to do all your joins and stuff.

 

For your sake, to import a database, I'm assuming what you're getting off codeplex is a SQL file.

You can import that directly into SQL Server through the management studio or through commandline (I forgot the exact command, but if you need, I could look it up).

KKirie MotobaFeb 06 2014, 03:17 AM

Well, it depends, will you beusing an Oracle or SQL Server?

There's a difference between a user that uses databases to do their jobs versus a Database administrator.

 

You can very well create queries and such to do reports from either a gui on Access, ASP based intranet website, etc. Usually, most users know how to do those, including myself, even though that's not my role.

On the other hand, you have a full fledged DBA, one that designs and recommends things to a project depending on their needs, does maintenance such as optimization, backups, replications, etc. And also analyzes the security updates released, does testing and certifies that it won't impact their production, and patch as required.

 

Knowing SQL is like the basics to almost any other positions in IT. On my end, one of my roles is being a SCCM administrator. SCCM relies entirely on SQL Server instances for all its databases, and in order to create reports, computer/user collections to deploy to, etc, I need to know WQL, which is a variant of SQL.

 

All the devs for internal applications need to know how to make their apps interact with a database, perform modifications as needed, etc.

 

Even project managers on their end, needs to understand the basics on how a database works in order to estimate costs and such for their project proposal and such. They may not know the technicalities and lean on an expert, but they need to at least understand the basics.
