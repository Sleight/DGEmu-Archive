Our Code Goals for 2010 are:StandardizationReducing database overloadReducing server overloadOh these are futuristic plans but we can surely handle them until the end of the year - I believe once we go through these stages we can shoot the site up with a better arcade, better member-integration, and better what-not else..Also these are only the code-wise goals.. We should also form a user-experience goals (skins, ajax, etc) and maybe content-goals (full arcade, rpg, ?).It's easy for me to form the code-wise goals because I'm a programmer and I can see rotten code right away :D anyway here are the goals in detail:Standardization:Well looking around the pages of the site - e.g. Mod utils, Warn editor, Moderator editor, etc I see a gigantic lack of standard in the pages look and feel, despite the fact that most of it was written but DJ and Atomic.. The look has nothing to do with the site or forums :( on the other hand some other pages like the moderator actions looks really good and use the forums template..So what simply has to be done is an overview of these tools a rewriting them as forum pages or as whatever you guys want that would not make people vomit when they see them.It's especially important when making improvements or fixes to certain parts of the code but since there are a billion code replications we either don't improve certain pages (not so bad..) or don't fix certain pages (could be very bad..)Same goes to stuff I've written - Though i'm pretty surprised to see the screenshotters and review inspections pages are using the sites layout (I remember I've written them more crappy-ish) there still are certain problems with it - for example hard-coded user-based login instead of database-based.. I'm going crazy at myself for writing it ;) ohhh the mistakes of the youth ;) I'm going to go over some of the code for the screenshotters and review inspection pages and see what if any required rewriting.. for permissions I'm going to set a table of permissions, containing a custom permission code (e.g. screenshotter will be 1, review inspector will be 2, etc..), user id, and a 32bit permission code (mostly 1 or 0 will be good, but when permissions can vary [e.g. screenshotter] a wider span is better). Plus I'll write a permissions handling class to handle that table so that talking with it will be e-a-s-y.Once that's done (hopefully within a week - like I said I don't have much time) I'll apply it to these 2 sections and we can go on developing such user-based sections..Reducing Database overload:You guys probably notice the few crashes we had lately.. this happens because of the sessions table corrupting due to over-kill of concurrent reads and writes..I'm currently looking for a solution for our sessions table - it's a very problematic table because it is being updated hundreds and in peak hours thousands of times a minute, what makes it a very possible bottleneck and in fact crashes the whole site when it goes down (because mysql won't start up with a corrupted table). How I fix it is I load mysql in a safe mode (can't be edited by non-root users) and truncate that table (can't repair it then again I don't care about it because it's content is meant to be temporary) and loads the database normally..Anyway I'm looking for a way to handle the sessions of the site and forums in different tables or something to reduce the throughput of this single ultra-raped fragile table.Reducing Server overload:Well another thing that could help is if our code will be efficient - less calls to database, more cache-oriented, so that the server itself (it's CPU and memory) would breathe more and so in peak hours could handle all those sessions manipulations without dying. Plus it would boost up the site loading time drastically. Maybe in normal time when a page takes less than 0.2s to generate we hardly notice but in peak hours the difference between 5s and 0.1s is noticable :) So like I said I'm going to go over the site's code and see what I can improve and where I can save DB-calls we don't need. Plus maybe reviving the old idea of a static, built every 2 minutes homepage, which I expect would do wonders (wonders!) to the server ;)

Standardization: Definitely agree with you completely on this. A number of the tools were written before I figured out how to use IPB's templating system, and so that's why they look ugly. The ones I went back and re-wrote are the pretty-looking ones :( I had wanted to fold all of that into an IPB3 upgrade, but I'm afraid that I'm currently unavailable to work on large projects (as I'm still in school and already handling large projects at work).Reducing database load: How much memory does the server have? Can we simply change the engine type for the session table to MEMORY to avoid disk I/O penalties (and hopefully any sort of data corruption at the filesystem level)? I suppose another solution is to throw more hardware at it, but that sounds expensive...How about newer versions of MySQL? Do they offer any sort of tangible performance benefits with regard to highly-concurrent applications? I think I remember hearing something about a new engine in MySQL 6 or something, but that's clearly not stable yet.Reducing server load: Agreed on this as well. Can we perhaps invest some time/effort into an opcode cache of some sort? Certainly a review of the entire codebase (with rewrites as necessary) is the correct long-term solution, but can we mitigate issues in the meantime by simply throwing in a cache? Of course, this assumes that the bottleneck (or at least part of it) is at the PHP level, which may or may not be the case.Generation of static pages at regular intervals sounds like a good idea to me. The only parts that really need higher resolution than that are comments (which aren't all that important in the grand scheme of things).
