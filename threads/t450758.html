Assuming it is his router it shouldn't just be zip files. It would just be that zip files happen to typically be large and downloaded sequentially on a single sustained connection instead of either being small or in pieces via a torrent. Thus if the router had a problem and the connection was reset in the middle of the download he would have a partial file but if a browser was loading a page and a connection was reset it would see that it didn't get one of the files and request it again.The basic problem with HTTP files transfers is that once the transfer has begun typically the server has no way of telling if the client is receiving unless it requests a resend and the client has no way of knowing if the transfer is finished unless it stops receiving. The server starts sending packets and the client responds with a ACK for each one it receives. If a response isn't sent the server just stops sending. Once the transfer is started there is no real bidirectional communication between the server and client and there are no provisions for resuming a transfer or error correction. Just the ability for the client to try resending an ACK if the connection is stalled. So with a HTTP transfer if the connection is reset the receiving machine assumes the download is finished and doesn't request the file again and the server assumes the transfer was canceled and doesn't try sending again. Unless you know how big the file is you won't notice a problem until you try to use it.The web as a whole would be better off if they upgraded the HTTP specs and included the features from a good transfer protocol like zmodem or its modern cousin sexyz. Browsers (and other clients) could easily implement the new standard while servers could just check the request header and maintain backwards compatibility. Then we could have browsers and web sites that could offer resumeable downloads, sliding packet windows (think what bit torrent does with a download only from a single source. Packets don't have to be received in order), error correction, batch transfers, and true bidirectional communication for transfers.Again, if it is his router it could be having memory issues and can't handle all the connections it is dealing with and some of them are getting dropped, it could be wireless signal issues (assuming a wireless router), a dying old router that is overheating and locking up temporarily, etc....And all of that is assuming it is his router dropping connections and not one belonging to his ISP. If his ISP wanted to screw with him these days it would almost be trivial to perform packet inspection and reset connections that are transferring any file that starts with standard zip header info.Of course it could also be issues with the line itself. Something causing interference or a damaged line causing data to go *POOF* before it ever makes it to the modem.And as always there is the possibility of windows simply being windows and eating parts of files because it thinks they taste delicious.
