Prompted by this topic: http://www.dgemu.com/forums/index.php?showtopic=213065Well, the fact of the matter is that acquiring hundreds of DPs is pretty much near impossible for most members. And I know that we've tried to create lots of opportunities to earn GPs and DPs by means other than posting, but I still kind of sympathize with some of them. So here's my suggestion: In exchange for x days of global DPs, we allow the option for one day of a higher reset, as determined by the number of days. This higher reset would still be lower than 12.5x (that is, the total amount of bandwidth that would be used were all 12.5 DPs to be used for each of the x days) to compensate for the instantaneous bandwidth usage and the fact that people don't usually use all 12.5 global DPs at once anyway. There would of course be restrictions as to when that higher reset occurs to prevent people from making a whole bunch of duplicate accounts, choosing the higher reset, and then cashing that in immediately.In terms of implementation, it's pretty simple. A new database table will be used to keep track of when to alter a member's DP reset for a certain period of time, and a simple task will automate that. The frontend may take a little bit longer, but it's certainly a feasible idea.So comments/suggestions?

AatomicknightMar 04 2007, 05:22 AM
Oh, and here's the missing implementation detail about how to calculate when to restore the global DP reset (assuming that we're going by the plan I suggested earlier). What you do is you generate the timestamp by using:time( ) + $days * 24 * 60 * 60where $days represents the number of days given up. Then, the task file calculates when the reset for the day the task is run takes place by using something like this:( ceil( time( ) / ( 24 * 60 * 60 ) ) ) * ( 24 * 60 * 60 )The idea is that the first half of the expression will give you the number of days that have passed and thus allow you to get the UNIX timestamp by converting days into seconds. Then you just execute the DP restore for any rows with a timestamp less than this cutoff time.Of course, this is all assuming that we're using the UNIX timestamp system that is normally used for these kinds of tasks. I see that another format has already been used in the existing table, but that might make things a bit trickier when dealing with two days in different months.
